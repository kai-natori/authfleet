# Design — agent plugin

## Layout (additions only)

```
packages/
  plugin/   NEW. The npm package `authfleet`: Better Auth server plugin
            factory `authfleet(options)` registering the read-only
            /authfleet/* endpoints inside a target app.
  core/     Gains HttpAgentReader + the formalized ProjectStatsReader
            contract. No behaviour change for D1 projects.
apps/
  api/      Registry schema gains project `type`; reader construction
            branches on type. Routes, snapshot cron and operator gate
            unchanged in shape.
  web/      Add-project form and type badges. No new routes.
```

## Decision: package home and name

The plugin lives in `packages/plugin` and is published as the unscoped
npm package **`authfleet`** (the name was free on npm when checked
2026-11-15; the monorepo root package stays private). The public entry
point is a factory matching Better Auth plugin conventions:

```ts
import { authfleet } from "authfleet";

export const auth = betterAuth({
  plugins: [
    authfleet({
      apiKeyHash: process.env.AUTHFLEET_API_KEY_HASH,
    }),
  ],
});
```

Rationale: one package, one import, named after the product. A scoped
package (`@authfleet/plugin`) was rejected — an extra scope buys
nothing for a single-package project and the unscoped name is the
memorable one. The plugin's peer dependency policy is recorded under
"Decision: Better Auth version policy" below.

## Decision: endpoint contract (versioned, counts only)

Endpoints are registered by the plugin under the target app's Better
Auth base path (default `/api/auth`), namespace `/authfleet`:

### `GET /authfleet/validate`

Returns `{ ok: true, version: 1 }`. Nothing else — no counts, no
config, no app metadata. The dashboard calls this at registration time
and whenever it needs to explain why an `agent` project is not showing
stats (unreachable vs. wrong key vs. old version are distinct UI
states).

### `GET /authfleet/stats?days=<n>`

`days` defaults to 30 (the window the dashboard's 7d/30d numbers are
derived from) and is clamped to a maximum of 90. Response body is the
v1 `UserStats` shape plus a contract version:

```jsonc
{
  "version": 1,
  "totalUsers": 1234,
  "anonymousUsers": 56, // or null when not detectable
  "dailySignups": [{ "date": "2026-11-14", "count": 12 }],
  "asOf": "2026-11-15T00:00:00.000Z"
}
```

This is byte-for-byte the contract `RemoteD1Reader.getUserStats()`
already produces (see `packages/core` `UserStats`), so
`buildStatsSummary`, snapshots and the dashboard need no changes.

Contract rules:

- **Counts only.** No endpoint returns user rows, emails, ids of
  individual users, or session data. This is a hard invariant, not a
  v1-of-the-plugin simplification.
- The `version` field is the contract version (integer, starts at 1),
  independent of the plugin package version. The dashboard supports a
  known set of contract versions; an unknown **newer** version is a
  distinct, explainable state ("plugin is newer than this dashboard —
  upgrade AuthFleet"), never a silent mis-parse.
- `anonymousUsers` follows the v1 rule: a number when the app's user
  model carries a detectable anonymous flag, otherwise `null` (the UI
  hides the split), never a fabricated zero.

## Decision: endpoint security (hashed key, timing-safe, no bypass)

- Each project gets its own API key: ≥32 bytes of CSPRNG output,
  generated by the operator (the dashboard's registration flow offers
  a generated key + the hash to paste into the app config; the key
  itself is shown once). Keys are per-project so one leak compromises
  exactly one target app's counts endpoint.
- The plugin never sees a stored plaintext key and never stores one:
  it is configured with `apiKeyHash` — the hex SHA-256 of the key —
  via plugin options, falling back to the `AUTHFLEET_API_KEY_HASH`
  environment variable.
- Verification: hash the presented `Authorization: Bearer` value with
  SHA-256 and compare against the configured hash with a timing-safe
  equality (`crypto.subtle` digest + constant-time compare of the two
  fixed-length digests). Missing/malformed header → `401`; the
  response body carries no detail about which check failed.
- The key and the `Authorization` header are never logged by the
  plugin. There is **no dev-mode bypass** in the plugin — unlike the
  api↔web dev bypass in v1, this code runs in other people's
  production auth servers, and a bypass flag there is a loaded gun.
  Local development uses a real throwaway key.
- Dashboard side: api only calls `https://` base URLs for `agent`
  projects (plain `http://` is accepted only for `localhost` in local
  development, mirroring the v1 local-dev exception), and treats the
  key with exactly the registry-credential discipline of v1 (decrypt
  in memory, use for one request batch, never return or log it).

## Decision: read inside the app via Better Auth's DB adapter

The plugin's endpoints obtain the app's DB adapter from the Better
Auth plugin endpoint context (`ctx.context.adapter` or its 1.x
equivalent) and count through the adapter's model API (`count`,
`findMany` with grouping done in code where the adapter cannot group)
against the **user model as Better Auth resolves it** — so custom
table names, custom field names and any supported database (Postgres,
MySQL, SQLite, D1, …) work without AuthFleet knowing the dialect.

Why not query the DB directly from the plugin: the plugin has no DB
credentials of its own and must not ask for any; the adapter is the
one sanctioned path and is what makes the plugin DB-agnostic.

### Research spike required (tasks group 1) — open questions

The adapter access pattern is the load-bearing assumption of this
change and is **not** treated as known. The spike must answer, against
Better Auth 1.4, 1.5, 1.6 and 1.7:

1. From a plugin endpoint handler, what is the supported way to reach
   the DB adapter (endpoint context shape), and does it differ across
   1.4–1.7?
2. How are the user **model name** and the **createdAt field name**
   resolved when the app customizes its schema (renamed model, renamed
   fields, `additionalFields`)? Is there an options/schema
   introspection API the plugin can use at init time?
3. How can the plugin detect an anonymous-flag field (the equivalent
   of v1's `is_anonymous` probing) through the adapter/schema, given
   the anonymous plugin may or may not be installed?
4. Can the adapter express "count per day over a window" efficiently,
   or must the plugin fetch `createdAt` values and bucket in memory?
   What is the safe upper bound (row cap / window cap) so a stats call
   cannot become a DoS against the host app?
5. Endpoint registration details: path composition under a custom
   Better Auth `basePath`, and whether endpoint middleware can run
   before the handler for the auth check on all `/authfleet/*` routes.
6. What does the plugin init hook receive, and can misconfiguration
   (missing `apiKeyHash`) fail loudly at startup instead of silently
   serving 401s forever?

Findings go into this design file (or a spike note linked from it)
before group 2 starts. If the adapter cannot support per-day signups
within safe bounds on some version, the fallback to record is:
contract v1 degrades `dailySignups` to totals-only on that version
(`dailySignups: []` with `totalUsers` correct) rather than dropping
the version from the support floor.

## Decision: registry — second project type `agent`

The `projects` table gains a `type` column (`'d1' | 'agent'`,
migration backfills `'d1'`). Per type:

| Field           | `d1` (existing) | `agent` (new)     |
| --------------- | --------------- | ----------------- |
| name            | ✓               | ✓                 |
| cfAccountId     | required        | null              |
| d1DatabaseId    | required        | null              |
| baseUrl         | null            | required (https)  |
| credential      | CF API token    | plugin API key    |
| tokenCiphertext | ✓               | ✓ (same columns)  |
| tokenIv         | ✓               | ✓                 |
| tokenHint       | last-4 of token | last-4 of API key |

The credential columns are reused deliberately: the encryption scheme
(AES-GCM, 256-bit key from `TOKEN_ENCRYPTION_KEY`, random 96-bit IV,
AAD `authfleet:project-token:v1:<projectId>`) is **unchanged** — the
AAD context string names the row binding, not the credential kind, so
no re-encryption or format migration is needed. `PublicProject` gains
`type` and `baseUrl` and omits the per-type fields that do not apply;
the API key is write-only exactly like the D1 token (never returned,
only the last-4 hint).

Validation at creation branches on type: `d1` keeps the v1 format
rules (32-hex account id, UUID database id); `agent` requires an
`https://` base URL (localhost http excepted in dev) and an API key of
at least 32 characters. Registration of an `agent` project performs a
`GET /authfleet/validate` call before saving, so a typo'd URL or key
fails at registration time with a specific message, not later as
mysteriously empty stats.

## Decision: one reader contract for both types

`apps/api` already depends on a structural reader shape
(`getUserStats(days?): Promise<UserStats>`). This change formalizes it
in `packages/core` as **`ProjectStatsReader`**, implemented by:

- `RemoteD1Reader` (existing, unchanged behaviour), and
- **`HttpAgentReader`** (new): constructed with `{ baseUrl, apiKey }`,
  calls `GET {baseUrl}/authfleet/stats?days=<n>` with the Bearer key,
  validates the response's contract `version` against the supported
  set, and maps failures to the same generic-error discipline as v1
  (detail server-side only — audit F3 applies here too: plugin error
  bodies are never forwarded to dashboard callers).

Api constructs the reader per project from its `type` in exactly the
two places readers are built today (stats routes and the snapshot
job). Snapshots therefore work for `agent` projects with zero changes
to the snapshot logic — growth history accrues from the day the plugin
is registered, same as for `d1` projects.

## Decision: read-only plugin (positioning and security)

The plugin is read-only **by design**, and this section records why
the Infra-style alternative was rejected.

Rejected alternative: _full admin parity with the official plugin_
(ban/delete users, session revoke, user listing). Rejected because:

- Write endpoints inside a user's auth server make the plugin a
  remote-admin backdoor whose key must be guarded like a root
  credential. A leaked read-only key discloses user _counts_; a
  leaked admin key owns the app. The support and security burden is
  not comparable.
- User listing/search necessarily exposes PII (emails, names), which
  breaks the counts-only invariant that makes AuthFleet easy to
  trust and easy to audit.
- "See all your projects" is the unmet need; user _management_ is
  already served by the official dashboard and by per-app Studio.
  AuthFleet's pitch stays: **if you just want to see, AuthFleet is
  the free self-hosted option; if you want to operate, use the
  official one.** Read-only is the positioning, not a missing
  feature.

For the same reasons this change also excludes audit-log/event
ingestion (a second data class with retention and privacy questions)
and any schema mutation in the target app (no activity-tracking
field): the plugin must be installable with the promise "it writes
nothing to your database".

## Decision: Better Auth version policy

- The plugin supports **Better Auth ≥1.4 <2** as a peer dependency —
  the same floor as `@better-auth/infra` (which requires ≥1.4) — and
  is tested against 1.4, 1.5, 1.6 and 1.7 in the fixture matrix
  (tasks group 3).
- The **endpoint contract version** (the `version` field) is versioned
  separately from both the plugin package and Better Auth: contract
  changes are additive within a version; a breaking change increments
  the contract version and the dashboard keeps reading the previous
  one for at least one AuthFleet release.
- A project whose plugin is absent (404 on `/authfleet/validate`),
  unreachable, or on an unsupported contract version is a first-class
  dashboard state ("plugin not found / unreachable / version
  mismatch"), shown on the project list and detail — never conflated
  with "0 users".

## Security follow-through

The v1 audit hardened the dashboard side; this change adds code that
runs **inside other people's auth servers**, which inverts the trust
direction: a bug in the plugin is a bug in every installing app's most
sensitive process. Therefore:

- The plugin ships with its own threat notes in `packages/plugin`
  (attack surface = two GET endpoints + one hash comparison; no
  writes, no PII, no outbound calls from the plugin).
- **Security audit round 2 is a required task group** (tasks group 8)
  covering the plugin and the new reader/registry surface, and it
  gates the first npm publish — the same discipline as v1, where the
  audit preceded any deployment.
